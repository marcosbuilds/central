# Design decisions — Central visual review

Status: decision implemented in the WPF/.NET 8 source and ready for human validation
Date: 2026-11-04
Scope: desktop shell, Home, project catalog, typography, responsiveness, and no-gateway states

This document is the current addendum to `docs/architecture/design.md`. It records the
decisions made for the requested review and separates what already exists in the
application from what depends on the future server.

## Visual direction

Central's hook is **“right context, clear next step.”** The interface does not
try to look like an activity feed or a control room full of signals. Home answers
three questions, in order:

1. what AI technical usage can be observed;
2. which project deserves attention now;
3. which requests the gateway may prove when it exists.

The result is a dark, quiet, editorial dashboard: a single surface for the
chart, a project card on the left, a coherent gate on the right, and request
logs below. Density comes from hierarchy and the table, not decorative counters.

## Implemented decisions

### Navigation

- `Current installation` is not part of the current shell.
- `Overview` was replaced by `Home`.
- The main menu exposes Home, Projects, and the selected project. People/sessions
  and settings are not first-level destinations.
- The current profile keeps a gear; it opens a centered visual-settings
  dialog with scrim, rounded border, and contained focus. `Esc` closes the dialog
  and returns focus to the trigger.
- The control to the right of the brand is a door vector with an arrow. The rail
  starts collapsed, fully hides the brand, and keeps only icons; when expanded,
  the brand and profile reappear. The transition is short and can be disabled by
  reduced-motion mode.
- Central's mark is an open “C”, without a third-party name or logo.

### Typography and assets

- Title roles use `SF Pro Display`/`SF Pro Text` when already present on the
  machine; the official fallback is `Segoe UI Variable`/`Segoe UI`. No Apple
  file is installed or redistributed without a license.
- Page titles and functional titles use `SF Pro Display`/Segoe fallback;
  subtitles, editorial labels, and short microcopy use Seloryn, bundled as a
  local WPF resource from the authorized repository. IDs, paths, commits, and
  code remain in Cascadia Mono. Validated asset hash:
  `3efcfff21b3fd204ee18378e1353d6b6c22d89dfea28a3734a7db5776981fb80`.
- Each project has its own vector mark in the catalog and focused card. The mark
  is part of the local model (`LogoPathData`), not an external package or dynamic registry.

### Home

- The two `local mode` cards and their associated button were removed.
- `Context Line`, `Observable Sequence`, and `Agents and states` were removed
  from Home so they do not compete with the main decision. Local Pulse remains
  available in project detail, where the simulation has appropriate context and inspection.
- The single chart is the screen's focal point. The selector offers 1 day, 7
  days, and 31 days; the visual contract reserves series for technical duration,
  tokens, and requests. Without a gateway, the state is explicitly `N/D`, with
  missing source and explanatory tooltip. There are no invented points, people
  rankings, or productivity inference.
- The card on the left shows only the focused project, mark, Seloryn name, I–V
  tier, and latest observable activity, with an external action to open the catalog/detail.
- The next gate is on the right: task, logical area, dependency, and permitted
  action. The column exists to help decide, not to fill space.
- Request logs follow the density of the reference but start empty. The header
  says that account/key data must be masked and that source, freshness, model,
  transport, status, and TTFT appear only when measured by the gateway.

### Responsiveness, contrast, and motion

- The window preserves a usable minimum width and can be maximized. On Home,
  the project card and next gate stack before becoming illegible; the log table
  keeps horizontal scrolling contained inside its own panel.
- Scrollbars have a dark thumb with visible hover/drag states; focus, caret, and
  text selection use light tokens. Green action buttons use dark text
  (`InkBrush`) to meet contrast.
- There is no loop, ticker, pulse, or auto-scroll. Animation is short and guides
  navigation. The user can enable `Reduce motion`.

## What remains deliberately unavailable

The dashboard does not claim that Claude, Codex, MCP, Git, CI, WebSocket,
PostgreSQL, or the gateway are already connected. `N/D`, `source not connected`,
and the absence of request rows are trust states, not visual failures. The plan
for turning these contracts into real streaming is in `docs/architecture/server.md`.

## Validation of this review

- Release build with no warnings/errors;
- existing xUnit suite passed;
- Home inspection in normal, compact, and maximized windows;
- inspection of expanded/collapsed rail, settings panel, catalog, search focus,
  scrollbars, and no-data states;
- verification that the publish and installer load the Seloryn font as an embedded resource.

## Second decision — AI coordination workbench (supersedes the previous IA)

Status: visual architecture decision approved for implementation; human acceptance pending
Date: 2026-11-04
Reason: human review and public-reference audit rejected Central as a generic dashboard with many equivalent destinations.

### Observed external evidence

- In Linear's public interface, side navigation is short and the work screen
  concentrates one object, its activity, and contextual conversation; no card
  grid competes for first attention.
- In the public VS Code repository on GitHub, file tree, branch, commit/history,
  README, and metadata appear in the same repository context; the side column is
  contextual, not a second global navigation.
- Public visual research on Pinterest was used only as a moodboard. It confirmed
  the dark-canvas/discreet-surface direction but did not authorize copying
  components or defining the flow.

These references are evidence of visual composition, not Central permissions,
data, or AI. The domain remains anchored in project documentation and local fixtures.

### Counterexample supporting the change

If Central exposes `Operate`, `Plan`, `Workspace`, `Coordination`, `Prove`,
`Publish`, and `Context` as seven equivalent destinations, a person must
memorize the taxonomy before they can work. The central use case — understand an
AI task, inspect the artifact, discuss it, and prove the result — is split across
screens that repeat the same project.

The decisive counterexample is: open `TASK-33`, notice that it depends on
`ADR-0004`, open the related file, ask an AI in the thread, and verify evidence.
If every step changes tabs and loses the selected object, Central fails at the
work it is meant to coordinate. The solution must reduce switching without
collapsing distinct states.

### Central-only hypothesis

Central is not a project manager with many modules. It is an **AI-and-human work
coordination workbench**. The project is the context boundary; the task and
artifact are the primary objects; conversation and proof close the loop.

```text
Home
├── compact global triage
├── selected focus + exceptions from other projects
├── AI technical usage (N/D until gateway)
└── request logs (honestly empty until gateway)

Projects
└── resolve identity and enter the explicit project

Project
├── Operate       next step, blocker, and permitted action
├── Workspace     tasks, reservations, files, Pulse, commits, tags, and releases
├── Coordination  local chat, contracts, and references
└── Prove         evidence, checks, history, and publication state
```

### What leaves primary navigation and where it continues

- `Plan` stops being a tab: tasks, criteria, dependencies, and reservations live
  in Workspace alongside the file and work they delimit.
- `Publish` stops being a screen: release, integration, and deployment appear as
  distinct states inside Prove; no local state receives the real-publication label.
- `Context` stops being a tab: decisions and observable history appear in the
  Workspace stream and Prove evidence line.
- `Operate` does not own the file tree; it answers only “what can move forward
  now?”. Workspace is the canonical owner of artifacts, tasks, and events.

This is not an aesthetic removal. It is a deliberate navigation-contract change
that prioritizes Central's specific work unit and keeps content accessible in the
correct context.

### Interface rules

- A project screen always shows name, ID, status, and revision in the header.
- Each reference resolves by semantic destination (`task`, `file`, `event`,
  `tag`, `release`, `delivery`); navigation never uses tab index.
- Workspace uses functional panels and selectable rows, not one card per item.
- Coordination looks like chat but continues to declare `local`, `pending`, or
  `unavailable`; it does not simulate streaming.
- Prove distinguishes `local release`, `local integration`, `locally approved`,
  and `unconnected deploy`.
- Home highlights only an explicitly resolved focus; without a source identifying
  the project/object, it does not create an aggregate exception strip or turn
  counts into priority.

### Direction rejection criteria

1. Select a project and return to Home showing a different `project_id`.
2. Fail to find a task, dependency, and criterion without opening a contextless sequence of screens.
3. Click a file, event, tag, or release and lose the selection in Workspace.
4. Interpret a local release as a deploy because the state is not explicit.
5. See more than one destination with the same visual emphasis without an explanation of its work.
6. Fail to use the rail, dialog, and chat with only a keyboard at 820×560 and 200% scale.
7. Show `0`, green, or `active` when the gateway source is absent.

### Motion and asset plan

- Rail: short width/opacity transition for spatial orientation only; the final
  state remains understandable without motion.
- Dialog: short opacity/scale entry/exit, static scrim, and contained `Tab`; reduced motion removes only the transition.
- Navigation icons: local geometry on a 24×24 logical grid, 16×16 safe area,
  consistent stroke, and no functional Unicode.
- Central logo: its own open C, separate from project logos; it is not a state indicator.

### Required additional validation

- Home → Projects → Project context check for every fixture;
- UI Automation/focus: rail, dialog, search, and chat;
- screenshots at 820×560, 1024×768, 1440×900, and maximized;
- inspection at 125%, 150%, and 200% scale when available;
- no-gateway, empty, partial, and error states without invented data;
- Release build, xUnit tests, and existing behavior tests.

## Third decision — Context Cursor

Status: implemented in source after adversarial review; human acceptance pending
Date: 2026-11-04
Reason: reduce the “generic dashboard” reading without hiding the local origin of data.

### Evidence and counterpoint

Inspection of the publish showed that the dark base, rail, and four modes were
coherent, but the same hierarchy was repeated through bands, cards, and notices.
The counterexample was a “neon control room”: many cards, seven equivalent
destinations, green states, an automatic stream, and unsourced metrics. It would
attract attention but contradict Central by making the person memorize the
taxonomy and possibly confusing a fixture with real activity.

The review team converged on a Central-specific hook: **an open C facing the
next step**. The C does not indicate success or presence; it indicates bounded
context with a clear passage to the next action. The product phrase remains
**“right context. clear next step.”**

### Source application

- The detail `Local context` banner was removed as an independent surface;
  honesty was not removed: `local fixture · gateway unavailable` appears inline
  in the project header.
- Workspace concentrates the workbench: files, inspector, tags/releases, and
  observable collaborators; at compact width, the order becomes files →
  inspector → metadata → tasks → commits.
- The catalog is no longer a stack of independent cards: it uses a list frame
  with dividers, its own logo, textual identity, and a single open command with
  a vector icon.
- Search uses a 24×24 vector path; controls contain no functional Unicode.
- Functional titles use Apple/Segoe; short subtitles and labels use Seloryn;
  technical text uses mono. This is a functional typography choice, not decoration.
- The no-gateway chart does not display `0`: every series is `N/D`, because
  absence is not measured zero.
- Delivery integration is enabled only when the delivery is locally approved
  and the project is open. References to task, file, revision, event, commit,
  tag, release, and delivery select the object and go to the canonical mode.
- The rail really starts at 78 DIP; when collapsed, the profile reduces to the
  gear, avoiding avatar/name clipping.

### Motion decision cards

| Motion | Purpose | Duration | With reduced motion |
|---|---|---:|---|
| Rail | spatial orientation between icons and labels | 170 ms | direct width, same final state |
| Selection/focus | show the current object | short, no loop | marker/contrast persist |
| Empty chart | feedback when changing period | 160–180 ms | state appears without fade |

None of these motions claims streaming, presence, or productivity. There is no
ticker, pulse, auto-scroll, or decorative animation.

### Falsifiable criteria for this decision

1. At `820×560`, Workspace must not create window-wide horizontal scrolling;
   panels must stack in the declared order.
2. Clicking each reference type must preserve object identity; a “located” toast alone is insufficient.
3. With empty `RequestLogs` and no gateway, there must be no request row or `0` presented as a measurement.
4. With a delivery in review, `Register integration` must be disabled; after
   local approval, enable it only with an open project.
5. Collapsing the rail must keep the entire gear inside its area; expanding must restore name and profile.
6. The interface must identify project, blocker, next action, and next gate within
   five seconds without using color as the only cue.

### Recorded validation

- Independent static review by information architecture, visual/interaction,
  and accessibility/responsiveness reviewers.
- Debug build after the change: 0 warnings, 0 errors.
- xUnit after the change: 12 passed.
- The final round still needs to replace old captures and record the viewport/
  scale sizes actually observed; this pending item is not treated as visual acceptance.

## Fourth decision — explicit identity before focus

Status: implemented in source after counterexample review; human acceptance pending
Date: 2026-11-04
Reason: remove a silent choice that contradicted the project-resolution contract.

### Counterexample and evidence

The local store started Home by automatically pointing to the first catalog item,
and the “next decision” card read `Tasks[0]`. This shortcut looks convenient in a
screenshot but fails when multiple projects exist: a person may interpret an
arbitrary fixture as their context and a task in review/blocked state as the next
permitted step.

The better-grounded counterexample is opening Central, seeing `Seloryn` by
chance, and performing an action while believing the context is `Sistema de
Vendas`. This violates the primary job of resolving identity and the rule against
mixing `project_id` between Home, catalog, and detail.

### Central-only decision

Home does not choose focus by seed order. It shows an operational empty state and
one next step: **resolve the project in Projects**. After explicit selection,
Home shows the selected project and derives the next decision from the first task
with `PRONTA` state; if none exists, it says there is no ready task instead of
promoting a blocked or in-review task to the recommended action.

This preserves the open-C hook: the C bounds context after it is chosen; it does
not invent context.

### Application and falsifiable checks

- `CentralStore` does not populate `SelectedProject` automatically.
- `CentralViewModel.FeaturedProject` is nullable and Home has a `NENHUM PROJETO EM
  FOCO` state with a catalog action.
- `ProjectModel.NextActionableTask` searches only `PRONTA`; `Tasks[0]` is no
  longer used for Home's decision.
- The `Operate` surface uses the same canonical property; the task shown in
  detail cannot diverge from Home triage.
- The empty state is keyboard-navigable and does not disable the catalog path.
- An automated test confirms a new session without a project, explicit selection,
  and resolution of `TASK-29` as a ready task.

## Fifth decision — honest Home before triage

Status: implemented in source after adversarial review; human acceptance pending
Date: 2026-11-04
Reason: remove a triage promise that was unsupported when no project was focused.

### Counterexample and evidence

In capture `14-home-no-focus-0.1.2.png`, the screen without a selected project
presented itself as `Triagem`, claimed `Um projeto em foco`, and showed `2
bloqueios`/`1 em revisão`. These were local aggregates without a project, task, or
gate. A person could open Projects but could not inspect the exception from Home.

The decisive counterexample is asking “which project should I open now?” and
receiving only aggregate counts. Calling this triage suggests an investigation
the surface does not provide; adding more cards or inventing project names would
fix the appearance but violate the Phase 1 data boundary.

### Central-only decision

Without an explicit project, Home is **Context**: it shows one next step,
`Open projects`, without aggregate counts that do not point to an object. After
the person chooses a project, the same route becomes **Triage**, with focus, the
next `PRONTA` task, and a summary of the selected project.

The empty state is no longer only a hidden component: mutually exclusive states
must not appear in the UI Automation tree. Central keeps the open C as a passage
mark but does not turn missing identity into priority.

### Application and falsifiable checks

- `HomeTitle` and `HomeSubtitle` change according to `FeaturedProject`; the phrase
  `Um projeto em foco` does not appear without focus.
- Without focus, the state is short and actionable; no names, counts, priorities,
  or inferred “next actions” are added.
- `AutomationStateGrid` and `AutomationStateBorder` use peers that remove
  descendants from the inactive branch; Home does not announce `FOCO ATUAL`/
  `PRÓXIMA DECISÃO` when the empty state is active, and Projects does not announce
  `Nenhum projeto encontrado` when results exist.
- Empty search and no-result filter states remain accessible and recoverable through `Clear search`.
- The executable exposes canonical version `0.1.2` in the assembly, manifest, and installer.

### Verification of this decision

- Debug build after the patch: 0 warnings, 0 errors.
- Native UI Automation observed on Home without focus and in the catalog with
  three projects: inactive-surface labels do not appear in `Document text`.
- No-result search observed with `0 resultado(s)`, empty panel, and `Limpar busca`; the catalog was restored after testing.
- Release validation, final viewport/scale captures, and human acceptance remain
  pending; this decision does not replace them.

## Sixth decision — compact empty state and accessible state

Status: implemented in source and republished as `0.1.2`; human acceptance pending
Date: 2026-11-04
Reason: publication review showed that Home still reserved space for unsourced modules and collapsed branches still appeared in the UI Automation tree.

### Counterexample and evidence

The counterexample is a visually “complete” Home that keeps axes, legends, a table
header, and a wide viewport when no gateway exists. The person sees the shape of a
dashboard but receives no measurement. This is worse than a short empty state: it
suggests missing telemetry and increases visual load without increasing the
possible decision.

The same rule appeared in Prove: a fixed three-column row pushed actions outside
the compact viewport. The delivery remained semantically correct, but the action
disappeared visually — a responsiveness counterexample that cannot be treated as
a finishing detail.

### Central-only decision

When the source does not exist, Central shows only what it can prove: `No
measurement`, the selected period, and `N/D`; numeric axes, legend, and point
tooltip are reserved for measured state. Request Logs collapses the table header
and viewport and shows a short empty state without converting absence to zero.

In Prove, each delivery uses a two-layer reading: identity/summary/status first,
and actions in a band that can wrap second. The action does not depend on a rigid
column and is not lost at compact width.

### Application and falsifiable checks

- `UsageChart` and `RequestTableViewport` remove inactive branches from the UI
  Automation tree; the empty state does not announce `HORA`, `CONTA`, axis `N/D`,
  or `agora`.
- Empty logs do not force `MinWidth=900` when there are no rows; horizontal
  scrolling remains confined to the table only when real records exist.
- Prove wraps actions in `WrapPanel`, keeping `Register integration` disabled for
  a delivery in review.
- The settings panel is a named, centered, rounded UIA window with scrim and
  focus return to its trigger.
- Lime action buttons render text tied to the button state's `Foreground`;
  enabled state uses `InkBrush`, disabled state uses unavailable text.

### Recorded verification for this round

- Release build: 0 warnings, 0 errors.
- Release xUnit: 12 passed.
- Self-contained win-x64 publish and installer output were generated only in
  ignored local build directories.
- UI Automation observed on the published Home: only the active empty state
  appears; collapsed chart axes and log header/rows do not appear in `Document text`.
- Home, Projects, Operate, Workspace, Coordination, Prove, and settings were
  traversed in the publish; Prove was observed at compact width with visible
  actions after reflow.
- 125–200% scale, formal screen-reader review, and human acceptance were not
  executed; they are not inferred from this round.
